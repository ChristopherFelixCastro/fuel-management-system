2. Propósito

Este documento indica exactamente qué entrega cada integrante, cómo se conectan los módulos, qué datos intercambian y qué evidencia demuestra que una tarea está terminada. No contiene código fuente: congela contratos y criterios verificables.

Flujo prioritario: Solicitud → aprobación → ticket QR → validación online → confirmación visual → despacho atómico → inventario → cierre → reporte/auditoría. Ningún extra puede romper este recorrido.

3. Principios comunes de integración

Arquitectura

Monolito modular API-first: .NET 8 Web API, módulos con límites claros y una única PostgreSQL. No microservicios ni BD por integrante.

Clientes

React + Vite + TypeScript. Portal administrativo y PWA de despacho; ambos consumen API, jamás PostgreSQL directamente.

Datos

EF Core + Npgsql, migraciones versionadas, DDL de referencia, constraints e índices. PostgreSQL es fuente transaccional de verdad.

Seguridad

JWT corto + Refresh Token Rotation; refresh hash/revocado/rotado. PasswordHasher ASP.NET Core Identity, nunca AES ni texto plano para passwords.

Gobierno

RBAC de un rol por usuario; auditoría append-only con IP, JSONB before/after y hash encadenado.

Entrega

GitHub monorepo: main, develop, feature/*; PR revisado, Swagger/OpenAPI y GitHub Actions con build/tests.

TLS protege tránsito; infraestructura protege reposo; RBAC limita datos sensibles. La PWA exige conectividad: no existe cola offline de validaciones ni despachos.

4. Convenciones REST

AspectoContrato
Base/rutas/api/v1; recursos plurales; acciones explícitas: /requests/{id}/approve.
JSON/datoscamelCase; UUID textual; DateTime ISO-8601 UTC; cantidades de galones decimal, nunca float.
Listas?page=1&pageSize=20&sortBy=createdAt&sortDirection=desc, tamaño 1–100; filtros explícitos de estado, fecha y recurso.
HeadersAuthorization: Bearer <jwt>, JSON, X-Correlation-Id opcional. POST despacho exige Idempotency-Key UUID.
HTTP200 lectura/acción, 201 creación, 400 validación, 401 sesión, 403 permiso, 404 inexistente, 409 conflicto/concurrencia, 422 negocio, 500 sin detalles internos.
ConcurrenciaAprobación, recepción, transferencia, ajuste y despacho son transacciones. Lock/version de ticket/tanque evita doble consumo. Reintento con igual key devuelve resultado original.

6. Roles, estados y reglas transversales

RolPermisosLímite
ADMINISTRADORUsuarios, maestros, configuración, dashboard/consulta.No reemplaza aprobación operacional ni despacho.
SUPERVISORCrea en nombre, aprueba/rechaza solicitudes, anula tickets, decide ajustes/cierres.Motivo obligatorio en rechazo, anulación y rechazo de cierre.
DESPACHADORValida QR, despacha en su estación, reporta ajuste, genera cierre.Debe tener estación; no bypass QR.
SOLICITANTECrea/cancela propia solicitud procedente y consulta.No aprueba ni modifica inventario.
AUDITORLectura, trazabilidad, reportes/exportaciones.Solo lectura; “Consulta” es capacidad, no sexto rol.
Invariantes: User ≠ Employee; no asignación permanente empleado–vehículo; vehículo requiere fuelType/capacidad/odómetro; despachador requiere estación; galones deben igualar exactamente lo autorizado; odómetro ≥ último; maestros soft delete; transacciones nunca delete. Existencia disponible = física − reservas de tickets activos. Consumir reduce física y libera reserva; vencer/anular libera reserva.
EntidadEstados
SolicitudBORRADOR → PENDIENTE → APROBADA → TICKET_GENERADO; PENDIENTE → RECHAZADA; BORRADOR/PENDIENTE → CANCELADA.
TicketACTIVO → CONSUMIDO, VENCIDO o ANULADO. Un ticket por solicitud; nunca DELETE.
CierreBORRADOR → PRESENTADO → APROBADO o RECHAZADO. Los intentos se preservan.

7. Iván — Core, autenticación, auditoría y despacho

Dueño backend transversalImplementa endpoints de despacho Servicios: AuthService, Response/Exception middleware, RBAC, Swagger, AuditService y DispatchService.

POST /api/v1/auth/login

Responsable/roles: Iván/anónimo. Request: {usernameOrEmail:string!,password:string!}. Valida: usuario activo y PasswordHasher. Data: {accessToken,expiresAt,refreshToken,user:{id,fullName,role,stationId?}}. HTTP: 200; errores: INVALID_CREDENTIALS, USER_INACTIVE. Audit: LOGIN_SUCCESS/LOGIN_FAILED. Nota: no se registra password.

POST /api/v1/auth/refresh · POST /auth/logout · GET /auth/me

Refresh: {refreshToken:string!}, rota/revoca anterior; 200 par nuevo o 401 REFRESH_TOKEN_INVALID/REVOKED. Logout: {refreshToken:string!}, idempotente y auditado. Me: Bearer; devuelve {id,fullName,email,role,employeeId?,stationId?,permissions[]}. Dependencia: Users/RefreshTokens de Christopher.

POST /api/v1/dispatches

Rol: DESPACHADOR de la estación. Headers: Bearer + Idempotency-Key. Request: {ticketId:UUID!,stationId:UUID!,tankId:UUID!,gallonsServed:decimal!,odometer:decimal!,confirmedAt?:DateTime,notes?:string}. Revalida en transacción: ticket ACTIVO/no vencido; estación asignada; tanque pertenece a estación y coincide combustible; cantidad exacta; odómetro no regresivo; físico suficiente; ticket no consumido. Bloquea ticket/tanque, crea Dispatch + InventoryMovement DESPACHO, reduce físico, libera reserva, CONSUMIDO y commit. Data: {id,ticketId,station,tank,gallonsServed,odometer,dispatchedAt,inventoryAfter,ticketStatus}. HTTP: 201 o 200 reintento. Errores: TICKET_EXPIRED, TICKET_CONSUMED, TICKET_CANCELLED, INVALID_STATION, FUEL_TYPE_MISMATCH, QUANTITY_MISMATCH, ODOMETER_REGRESSION, INSUFFICIENT_PHYSICAL_STOCK, CONCURRENCY_CONFLICT. Consume: PWA Christopher; depende Gabriel/José/BD.

GET /api/v1/dispatches · GET /api/v1/dispatches/{id}

ADMINISTRADOR/SUPERVISOR/AUDITOR; DESPACHADOR solo su estación. Filtros stationId,tankId,ticketId,from,to,paginación. Devuelve historial inmutable; 200/404; audit de consulta sensible si se acuerda.

9. Gabriel — Solicitudes, tickets, QR, PDF y notificaciones

POST/GET /api/v1/requests · GET/PATCH /api/v1/requests/{id}

Crean: SOLICITANTE propio, SUPERVISOR por empleado, sistema automática/recurrente. POST: {employeeId,vehicleId,departmentId,fuelTypeId,requestedQuantity,requestedFor?,source:"MANUAL"|"SUPERVISOR"|"AUTOMATIC"|"RECURRENT",notes?}. Reglas: coherencia empleado/vehículo/departamento; fuelType coincide vehículo; cantidad >0 y ≤ capacidad; crear no exige stock. PATCH solo BORRADOR/PENDIENTE por autor/supervisor. Errores: VEHICLE_FUEL_MISMATCH, QUANTITY_EXCEEDS_TANK_CAPACITY, DEPARTMENT_INCOHERENT, REQUEST_NOT_EDITABLE.

POST /api/v1/requests/{id}/approve · /reject · /cancel

Approve: SUPERVISOR; {authorizedQuantity,expiresAt,notes?}. PENDIENTE, autorizado ≤ solicitado/capacidad, disponibilidad suficiente; reserva exacta y genera único ticket COM-{AÑO}-{6 dígitos} reiniciado anual. Data request+ticket. Errores REQUEST_NOT_PENDING, INSUFFICIENT_AVAILABLE_INVENTORY, TICKET_ALREADY_EXISTS, EXPIRATION_INVALID. Reject: {reason!}. Cancel: dueño/supervisor antes del ticket; CANCELADA. Transiciones auditadas; depende inventario José.

GET /api/v1/tickets · GET /tickets/{id} · GET /tickets/{id}/pdf

Dueño solicitante, SUPERVISOR, DESPACHADOR aplicable, AUDITOR/ADMIN. Filtros number,status,employeeId,vehicleId,from,to. Data: {id,number,requestId,employee:{name,employeeNumber},vehicle:{plate},fuelType,authorizedQuantity,expiresAt,status,qrToken}. PDF application/pdf; errores TICKET_NOT_FOUND, TICKET_ACCESS_DENIED, PDF_GENERATION_FAILED.

POST /api/v1/tickets/validate · POST /tickets/{id}/cancel

Validate: DESPACHADOR, {qrPayload,stationId}. QR compacto ticketId/token/firma; BD es verdad. Verifica firma, ACTIVO/vencimiento y no consume. Devuelve visual obligatorio {ticketId,number,employee:{name,employeeNumber},vehicle:{id,plate},fuelType,authorizedQuantity,expiresAt,status,canDispatch,validationId}. Bloqueos: TICKET_EXPIRED, TICKET_CONSUMED, TICKET_CANCELLED, QR_SIGNATURE_INVALID, TICKET_NOT_FOUND; sin bypass. Cancel: SUPERVISOR, {reason!}, ANULADO y libera reserva. SMTP/SMS mock tras eventos; falla INTEGRATION_FAILURE no revierte transacción.

10. José Enrique — Inventario, recepción y ajustes

/api/v1/stations, /tanks, /suppliers — CRUD + deactivate

Mutar: ADMINISTRADOR. Station {code,name,address?,isActive?}; Tank {stationId,code,fuelTypeId,maxCapacity,currentQuantity,criticalLevel,isActive?}; Supplier {rnc,name,email?,phone?,isActive?}. Tanque pertenece a estación y tiene un combustible; 0≤actual≤capacidad, crítico≤capacidad. Errores TANK_CAPACITY_EXCEEDED, TANK_FUEL_TYPE_REQUIRED, DUPLICATE_TANK_CODE, RNC_ALREADY_EXISTS.

POST/GET /api/v1/receptions

SUPERVISOR. POST {supplierId,stationId,tankId,invoiceNumber,receivedAt,volume,rnc,notes?}. Tanque-estación correcto, volumen >0, no excede capacidad, factura única proveedor. Transacción: saldo + movimiento RECEPCION. Errores TANK_OVER_CAPACITY, INVOICE_ALREADY_REGISTERED, INVALID_RECEPTION_TANK.

GET /api/v1/inventory · GET /inventory-movements

ADMIN/SUPERVISOR/AUDITOR; DESPACHADOR su estación. Inventario: {tankId,station,fuelType,physicalQuantity,reservedQuantity,availableQuantity,criticalLevel,lastUpdatedAt}. Ledger filtrable tankId,type,referenceType,from,to y paginación; inmutable.

POST/GET /api/v1/transfers

SUPERVISOR. {sourceTankId,destinationTankId,quantity,transferredAt,notes?}. Tanques distintos/mismo combustible; físico fuente y capacidad destino. Una transacción crea TRANSFERENCIA_SALIDA y TRANSFERENCIA_ENTRADA relacionadas. Errores TRANSFER_FUEL_MISMATCH, INSUFFICIENT_PHYSICAL_STOCK, DESTINATION_OVER_CAPACITY.

POST/GET /api/v1/adjustments · POST /{id}/approve · /{id}/reject

DESPACHADOR reporta {tankId,physicalQuantity,reason,evidenceUrl?}; SUPERVISOR decide. PENDIENTE; approve crea AJUSTE_POSITIVO/NEGATIVO, reject exige motivo y preserva intento. Diferencia negativa no se vuelve merma automáticamente. Errores ADJUSTMENT_NOT_PENDING, ADJUSTMENT_REJECTION_REASON_REQUIRED, PHYSICAL_QUANTITY_INVALID.

GET /api/v1/reports/consumption, /inventory, /traceability · GET /api/v1/exports/{reportType}

ADMIN/SUPERVISOR/AUDITOR. Filtros: from,to,employeeId,vehicleId,departmentId,fuelTypeId,ticketStatus,stationId. Export añade format=pdf|xlsx|csv. Errores REPORT_FILTER_INVALID, EXPORT_FORMAT_UNSUPPORTED, EXPORT_GENERATION_FAILED. Read-only y audit EXPORT_GENERATED.

17. Checklist de integración final y demo

Checklist

  • RBAC cinco roles, audit hash append-only, no DELETE de transacciones.
  • Reserva/consumo/liberación reconciliados; concurrencia/idempotencia superadas.
  • PWA online bloquea QR inválido/offline; portal y API desplegados.

Happy path de demo

  1. Solicitante crea solicitud válida.
  2. Supervisor confirma stock, autoriza cantidad/vencimiento; reserva y ticket COM QR/PDF.
  3. Despachador de estación escanea, confirma empleado/ficha/placa/fuel/cantidad/vencimiento.
  4. Registra cantidad exacta y odómetro; servidor revalida, despacha, reduce físico/libera reserva/audita.
  5. Genera cierre; supervisor aprueba; auditor filtra y exporta trazabilidad.
