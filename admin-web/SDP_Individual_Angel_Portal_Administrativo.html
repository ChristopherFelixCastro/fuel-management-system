1. Propósito y alcance individual

Angel entrega la experiencia visual y operativa del portal administrativo web. Este portal permite a los perfiles autorizados consultar indicadores y administrar los maestros de usuarios, empleados, vehículos y departamentos, sin romper las reglas de seguridad, inventario y trazabilidad establecidas para el sistema.

Principio de alcance: el portal es un consumidor de la API REST. No implementa acceso directo a PostgreSQL, no genera tickets QR, no ejecuta el despacho PWA y no duplica las validaciones definitivas del backend.

Incluye

  • Layout general, navegación, experiencia visual y rutas protegidas del portal.
  • Dashboard ejecutivo con indicadores de inventario, tickets activos y consumos por departamento/vehículo.
  • CRUD de Usuarios, Empleados, Vehículos y Departamentos.
  • Asignación de rol a usuario, filtros, paginación, estados y mensajes de error.
  • Pruebas funcionales del portal y participación en pruebas integradas.

No incluye

  • Modelo físico, scripts SQL/migraciones y PWA de despacho: Christopher.
  • Core API, autenticación, autorización y auditoría: Iván.
  • Solicitudes, tickets, QR, notificaciones y PDF: Gabriel.
  • Recepciones y operaciones de inventario: José Enrique.
  • Cierres, alertas, reportes y exportación: Jaime.

3. Arquitectura técnica del portal

Cliente: React + Vite + TypeScript. El portal se construye con componentes reutilizables, rutas protegidas, cliente HTTP centralizado y DTOs tipados conforme al OpenAPI de la API .NET 8. Su comunicación ocurre mediante HTTPS con JWT de vida corta; la renovación de sesión sigue el contrato seguro definido por Iván.

Capas de interfaz

  • Aplicación/rutas: guardas de sesión y rol.
  • Layout: menú lateral, cabecera, breadcrumb y área principal.
  • Componentes comunes: tablas, filtros, formularios, modal de confirmación, alertas y estados de carga.
  • Features: Dashboard, Usuarios, Empleados, Vehículos y Departamentos.
  • Servicios: cliente API, tipado de DTOs y normalización de errores.

Reglas de UX y seguridad

  • RBAC visual: se ocultan acciones no permitidas, pero API decide siempre.
  • Formularios validan para orientar; API y BD vuelven a validar.
  • No se expone password hash, refresh token, auditoría sensible ni cadenas de conexión.
  • Acciones relevantes usan confirmación; éxito/error queda visible y comprensible.
  • Estados desactivados se muestran; no se usa eliminación física desde el portal.

Flujo administrativo base

Login
JWT / rol
Ruta protegida
Consulta API
Formulario validado
Confirmación / feedback
  1. El usuario inicia sesión mediante /auth; el portal obtiene sesión conforme al contrato seguro.
  2. Las rutas y menú se configuran según rol; por ejemplo, no se ofrecen acciones de administración a un DESPACHADOR.
  3. La pantalla solicita el listado o detalle con filtros/paginación.
  4. Al guardar, el portal envía únicamente el DTO permitido y presenta la respuesta oficial.
  5. Ante 401, sesión vencida: volver a autenticación/renovar conforme a API; ante 403, informar falta de permiso; ante validación, mostrar errores de campo; ante red, preservar lo escrito cuando sea posible sin asumir que se guardó.

Usuarios

Permite listar, buscar, crear, editar, activar/desactivar y asignar un único rol por usuario: ADMINISTRADOR, SUPERVISOR, DESPACHADOR, SOLICITANTE o AUDITOR. Para DESPACHADOR, la estación es obligatoria. El formulario no muestra ni modifica password_hash o refresh tokens; la definición de credenciales sigue el flujo seguro de Iván.

5. Endpoints y contratos consumidos

Las rutas exactas se consolidan en Swagger/OpenAPI con Iván. Angel consume contratos; no crea una API paralela.

Autenticación/authLogin, sesión y logout/renovación bajo contrato.
Usuarios/usersListar/consultar/crear/editar/activar-desactivar, con RBAC.
Empleados/employeesCRUD y filtro por departamento/estado.
Vehículos/vehiclesCRUD, tipo combustible, placa, odómetro y estado.
Departamentos/departmentsCRUD/estado y catálogos.
DashboardEndpoints de resumen acordadosLecturas agregadas de inventario, tickets y consumos.

Los DTOs de escritura excluyen campos derivados, hashes y datos de auditoría. Filtros, ordenamiento y paginación deben ser server-side si el contrato lo provee. Cada mutación devuelve una respuesta que el cliente usa para refrescar la vista, sin actualizar optimistamente datos críticos de forma irreversible.

6. Criterios de aceptación, pruebas y Definition of Done

Criterios de aceptación

  • Portal responsivo, con navegación coherente y acceso protegido según sesión/rol.
  • CRUD completo de las cuatro entidades asignadas, con validaciones, búsqueda/listado y activar/desactivar.
  • Usuario tiene exactamente un rol; DESPACHADOR exige estación; vehículo exige tipo de combustible.
  • Dashboard muestra indicadores oficiales y maneja carga, vacío, error y filtros aplicables.
  • Los permisos, validaciones críticas y soft delete se respetan aunque alguien altere la interfaz.
